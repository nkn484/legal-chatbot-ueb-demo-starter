# M08.3.2 — Automatic Controlled Corpus Expansion

> **Architecture specification only — not implemented code.**
>
> Governing principle: humans approve a SOURCE and a bounded, machine-enforceable POLICY; the
> system automatically discovers, verifies, fetches, versions, and ingests DOCUMENTS only when they
> deterministically satisfy that active source/policy.

## 1. Decision and scope

M08.3.2 changes the approval unit from an individual document to a versioned source policy. It is not
permission for an LLM, user, search result, or adapter to browse or fetch arbitrary Internet content.
The canonical corpus may grow automatically only inside a deliberately narrow authority envelope.

**Verdict: `GO_WITH_CONDITIONS`.** This is a target design, not an implementation authorization or
claim. Activation requires the phase gates below, including a TLS-valid official route and M08.2
Phase B for temporal legal answers.

## 2. Difference from M08.3.1

M08.3.1 remains the baseline for immutable provenance, safe helpfulness, exact acquisition,
source-isolated retrieval, citations, privacy, and temporal failure behavior.

| Topic | M08.3.1 | M08.3.2 target |
|---|---|---|
| Approval unit | Exact document/ref after review | Active source plus bounded compiled policy |
| Candidate | Human/user gate before fetch | Automatic if deterministically policy-matched |
| Discovery | Exact approved number only | Named deterministic policy templates only |
| Fetch authority | Manifest `FetchApprovedDocumentRef` | Server-issued short-lived `PolicyAuthorizedFetchRef` |
| Evidence path | Canonical ingest then normal retrieval | Unchanged; no temporary official evidence |
| Source authority | Registry/manifest | Registry remains upper authority; policy only narrows |

M08.3.2 removes per-document approval only for documents that satisfy an active approved policy. It
does not remove explicit human/user approval for a source, transport, adapter capability, policy
revision, widening change, or revocation reversal.

M08.1 remains constrained to bounded internal lexical retrieval. Its planner cannot create a source,
URL, endpoint, document identity, legal metadata, or usable fetch authority. This specification
replaces the prior unsafe corrective prompt: no LLM-generated arbitrary search and no dynamic fetch
authorization without a compiler and server-issued grant.

## 3. Coverage goals are separate

1. **Helpful-response coverage ≥95%** means a valid request gets an official answer, labeled
   institutional-policy guidance, labeled reviewed guidance, clarification, escalation, or useful
   no-evidence response.
2. **Official-grounded legal-answer coverage** counts only answers with `OFFICIAL_LEGAL` evidence,
   valid immutable provenance, persisted server citations, successful citation revalidation, and a
   supported temporal scope. It is measured, never promised at 95%.

Release safety targets remain: safe terminal response for 100% of valid requests, unsafe legal claims
without official evidence = 0, official citation revalidation = 100%, and provenance mislabeling = 0.
Corpus growth may improve future internal hits but cannot upgrade a helpful fallback to official law.

## 4. Retained boundaries and registry authority

- `LLMProviderPort`, `LegalSourcePort`, and `ChannelPort` remain mandatory boundaries.
- Chat, Retrieval, Citation, and Conversation must not import SHINE SHOP, Anthropic, SOAP, REST, or
  Zalo SDK clients. Transport-specific code stays in source/channel/provider adapters.
- Source registry is upper authority for lifecycle, transport, origin, operations, and access mode;
  source priority is rollout order, not legal-authority ranking.
- Registry order remains VBQPPL priority 1 (`ACTIVE`, `DEMO_NOW`), VNU priority 2 (`PLANNED`,
  `LATER`), and UEB priority 3 (`PLANNED`, `LATER`). A policy cannot activate VNU/UEB or add a source.
- The policy cannot widen a registry host, transport, endpoint, operation, access mode, or source
  lifecycle. If the registry says `READ_ONLY_ALLOWLIST`, a policy cannot create broad read authority.
- Policy-authorized document automation requires a separately user-approved registry capability such
  as `READ_ONLY_POLICY_ALLOWLIST` for the exact source, transport, and operations. Inside that mode, an
  active compiled policy is document-level authority only within the capability explicitly granted by
  the registry. Legacy exact manifest references remain valid.
- A source that remains `READ_ONLY_ALLOWLIST` is manifest-only and cannot accept policy grants.
  Adapters must not accept `PolicyAuthorizedFetchRef` through generic type widening; they may accept it
  only through the mandatory pre-I/O policy/grant guard after registry migration, compiler validation,
  and explicit user approval for that source capability.
- The canonical document/version/chunk/provenance store remains the only official corpus; no crawler
  store, temporary evidence store, or parallel answer path is introduced.

## 5. Evidence classes and source isolation

Evidence class is immutable server-owned provenance, never an LLM/user decision.

| Class | Official legal answer? | Rule |
|---|---:|---|
| `OFFICIAL_LEGAL` | Yes | Canonical official source, immutable provenance, server citations |
| `INSTITUTION_POLICY` | No | Separate lane; owner/version and non-official label |
| `USER_SUBMITTED` | No | User-provided; never verified law by default |
| `REVIEWED_GUIDANCE` | No | Labeled guidance; no legal citation claim |
| `UNTRUSTED_DISCOVERY` | No | Staging only; never answer evidence |
| `NONE` | No | Clarification, escalation, refusal, or no-evidence |

Production official retrieval selects only active registry sources and eligible, non-quarantined
`OFFICIAL_LEGAL` versions. Institutional, user, guidance, discovery, test, and synthetic content stay
separate. They cannot borrow VBQPPL provenance, official citation format, or legal-authority status.

## 6. Threat model

Assume an attacker may be a user, LLM output, malicious document, compromised discovery endpoint,
overly broad policy author, or unstable upstream source.

| Threat | Required control |
|---|---|
| User/LLM supplies attacker or private URL | User URLs prohibited; server policy/adapter constructs requests |
| SSRF by host/path/DNS/redirect/IP literal | Registry plus compiled allowlists, address checks, redirects denied |
| TLS interception/downgrade | HTTPS and `verify=true`; no trust bypass |
| Discovery result pretends to be law | `UNTRUSTED_DISCOVERY` is non-evidence and non-fetch-capable |
| Prompt injection in question/XML/HTML | All external text is data; deterministic parsers, no tool instruction execution |
| Poisoning/identity collision | Deterministic validation, immutable provenance/hash, quarantine/revocation |
| XML/HTML bomb | Parser isolation; entity, byte, depth, node, time, compression bounds |
| Regex DoS | Bounded safe matchers compiled at load time |
| Cost/outage abuse | Calls/results/docs/depth/time/rate caps and circuit breaker |
| Replay/race duplicates | Advisory lock, coalescing, immutable uniqueness, idempotent recheck |
| Privacy leakage | Content-free audit; no raw question/planner/search/candidate text |

An official endpoint is not assumed complete, current, available, or semantically safe merely because
it is official. A policy bounds authority; it is not proof of legal completeness.

## 7. Current source limitation

The current VBQPPL SOAP TLS path is blocked. A `verify=false` diagnostic is non-promotable and
produced **0/32**. A policy never overrides source TLS failure, certificate failure, outage, or adapter
validation failure.

Current VBQPPL capability is exact-number-only. It cannot magically support title/concept/synonym
discovery. The first viable policy can therefore only permit exact-number recovery. Title or concept
discovery requires a separately approved active registry capability, documented adapter, bounded
official template, Oracle gate, and explicit user approval. No policy may claim an unsupported source
capability.

For `EXACT_DOCUMENT_NUMBER`, every discovery input must come from a finite, versioned,
policy-enumerated server-owned set. A number grammar or bounded family may validate returned candidate
metadata, but it cannot generate or authorize a new discovery request number. Only
`FIXED_OFFICIAL_INDEX` may produce previously unknown numbers, and only after its separate
registry/adapter/template approval.

## 8. Versioned approved source policies

The proposed reviewed contract is `contracts/approved-source-policies.json`. It is versioned and
fail-closed. Chat requests, planners, discovery output, adapters, and reviewer recommendations cannot
create or edit it. Revisions are immutable; a replacement has a new version.

Each `ApprovedSourcePolicy` requires:

```text
policy_id, version, owner, status, source_id,
effective_from, effective_to, revocation status/reason,
transport, normalized host, endpoint/path, action/operation,
TLS settings, discovery mode/template,
document constraints, allow rules, deny rules, bounded limits
```

Illustrative shape:

```json
{
  "policy_id": "vbqppl-exact-number-v1",
  "version": 1,
  "owner": "legal-source-governance",
  "status": "ACTIVE",
  "source_id": "VBQPPL",
  "effective_from": "2026-08-21T00:00:00Z",
  "effective_to": "2026-12-31T23:59:59Z",
  "revocation": {"status": "NOT_REVOKED", "reason_code": null},
  "authority": {"transport": "SOAP", "host": "ws.vbpl.vn", "endpoint": "/vbqppl.asmx", "action": "GetListVanBanByListSKH"},
  "tls": {"https_only": true, "verify": true},
  "discovery": {"mode": "EXACT_DOCUMENT_NUMBER", "template_id": "vbqppl_soap_number_v1"}
}
```

Only a currently effective `ACTIVE` policy can authorize work. Valid lifecycle states are `DRAFT`,
`ACTIVE`, `SUSPENDED`, `EXPIRED`, and `REVOKED`. `REVOKED` is terminal for that revision; a new
explicitly approved revision is required for any replacement.

### 8.1 Deterministic discovery policy

Discovery is an enum, not executable text. Initial allowed modes are:

- `EXACT_DOCUMENT_NUMBER`, using a named adapter-owned request template; and
- `FIXED_OFFICIAL_INDEX`, only when registry and adapter document fixed filters, deterministic
  pagination, a bounded official index, and a named template.

Template IDs select code-owned request builders. Policy values are bounded template parameters only;
they cannot include arbitrary URLs, endpoint fragments, headers, SOAP/XML bodies, SQL, scripts,
regular expressions, or LLM text. A missing adapter capability/template is a compile rejection.

### 8.2 Document constraints, allow, and deny

The policy must specify deterministic applicable constraints for:

- document-number grammar plus a finite, versioned, server-owned input set for exact-number discovery;
- normalized title finite set or safe bounded matcher;
- document type, issuing authority, and jurisdiction allowlists;
- promulgation/publication/effective date ranges where available;
- external ID, canonical path grammar, and canonical origin;
- content type, decoded-byte cap, encoding, hash/parser profile, and required identity fields; and
- allow selectors plus explicit deny selectors for identity, type, issuer, date, and path.

Deny always wins. A candidate must match every required constraint and at least one allow selector.
Missing required metadata, ambiguous identity, conflicting fields, or unsupported normalization rejects.

The compiler rejects broad/unbounded rules: wildcard hosts, arbitrary endpoint prefixes, arbitrary
numbers, `.*` title matching, unlimited dates/pagination/content, absent issuer/type/jurisdiction
constraints, unbounded relations, unsafe regex, or action outside the registry. A low rate limit does
not make a broad policy safe.

### 8.3 Mandatory hard limits

Every policy has positive finite values for:

```text
max_calls_per_request, max_calls_per_policy_window,
max_results_per_discovery, max_documents_per_request,
max_relation_depth, max_elapsed_seconds, request_timeout_seconds,
rate_limit_per_window, circuit_breaker_failure_threshold, circuit_breaker_open_seconds
```

Runtime limits are shrink-only. Relation expansion is permitted only for named policy relation kinds;
each child must independently match an active compiled policy. There is no recursive crawl fallback.

## 9. `ApprovedSourcePolicyCompiler`

`ApprovedSourcePolicyCompiler` deterministically accepts the reviewed contract, active source registry
snapshot, adapter capability table, and server clock. It emits immutable `CompiledApprovedSourcePolicy`
or a precise rejection code. It makes no network or LLM call.

Compilation must:

1. validate schema, canonical serialization, unique versions, owner, status, effective period, and
   revocation;
2. resolve an `ACTIVE` registry source and prove policy transport/host/endpoint/action/access mode is
   an equal-or-narrower subset of registry and adapter capabilities;
3. validate discovery template, bounded safe matchers, constraints, allow/deny selectors, and limits;
4. reject empty, broad, ambiguous, expired, suspended, revoked, or conflicting policy intersections;
5. emit canonical policy/registry/adapter-capability digests, immutable predicate/request-builder ID,
   effective interval, and budgets.

The compiled object is server-owned and read-only. Cache keys include policy digest and registry
snapshot. Any registry, policy, adapter-capability, or relevant-time change invalidates compilation.
Runtime can only tighten a cap; it cannot patch or widen compiled authority.

## 10. Server-issued fetch grant

A discovery candidate is never a fetch reference. Only after deterministic policy and identity
validation may the authorization service issue a server-held, short-lived, single-purpose
`PolicyAuthorizedFetchRef` (grant).

```text
grant_id, policy_id, compiled_policy_digest, registry_digest,
source_id, transport, action, canonical external_id/path,
normalized verified identity, issued_at, expires_at,
single-use nonce, maximum request count, acquisition correlation ID
```

The grant is opaque outside the server boundary, integrity protected, expires quickly, and is not a
reusable client capability. It is not accepted from a user, channel payload, prompt, LLM, discovery
result, or client storage. Knowing its shape cannot construct usable authorization.

Immediately before every network I/O, the service/adapter revalidates grant integrity/expiry/use,
active registry source/transport/host/action, compiled policy digest/effective period, candidate
identity, endpoint/path, TLS, budget, rate limit, and circuit state. Failure produces zero unauthorized
I/O and invalidates or consumes the grant as appropriate. A grant authorizes neither siblings,
redirects, other transports, nor future retries after expiry.

## 11. Human approval versus automation

### Automatic only under an effective compiled policy

- corpus-gap detection after local retrieval and deterministic recovery;
- deterministic policy route/template selection and bounded discovery;
- non-evidence staging, identity/content validation, grant issuance/revalidation, TLS-valid fetch;
- canonical ingestion, dedupe/new immutable version, normal retrieval, persisted citations, and answer;
- deterministic quarantine on integrity failure.

### Always explicit human/user approval

- source registry/addition/activation/retirement; host, transport, adapter, or official-authority change;
- policy creation, activation, widening, replacement, expiry renewal, un-revocation, template, document
  family, relation depth, or budget-ceiling change;
- VNU, UEB, institutional, user, guidance, or discovery lane promotion;
- M08.2 Phase B legal-effect data and temporal activation; and
- each rollout phase after its Oracle gate.

A reviewer recommendation does not replace explicit user approval of a source/policy change. Individual
document approval is unnecessary only when the active approved policy deterministically covers it.

## 12. Required workflow

```text
conversation reservation + temporal guard
  -> local source-isolated retrieval
  -> deterministic retrieval recovery
  -> evidence sufficiency
  -> CORPUS_GAP
  -> deterministic route/compiled-policy match
  -> controlled discovery via LegalSourceDiscoveryPort
  -> UNTRUSTED_DISCOVERY staging (not evidence)
  -> deterministic policy/identity validation
  -> server-issued PolicyAuthorizedFetchRef
  -> grant revalidation before network I/O
  -> TLS-valid official fetch via LegalSourcePort
  -> canonical immutable ingestion
  -> normal source-isolated retrieval
  -> persisted RetrievalRun + CitationRecord
  -> grounding + citation revalidation
  -> answer, clarification, escalation, or no-evidence response
```

There is no discovery/fetch/staging-to-answer shortcut:

```text
temporary external passage != official evidence
discovery candidate != citation
fetched but un-ingested document != citation
LLM statement != legal metadata
```

## 13. State machines

### 13.1 Policy state

```text
DRAFT -> USER_APPROVAL_PENDING -> APPROVED_PENDING_COMPILE -> ACTIVE
ACTIVE -> SUSPENDED -> ACTIVE                 (only within original effective period)
ACTIVE | SUSPENDED -> EXPIRED
ACTIVE | SUSPENDED | EXPIRED -> REVOKED       (terminal for this revision)
invalid compile/rejected proposal -> REJECTED  (terminal; new revision required)
```

Only an effective `ACTIVE` compiled policy authorizes discovery or grants. Revocation cannot be
reversed in place.

### 13.2 Candidate/acquisition state

```text
CORPUS_GAP -> POLICY_ROUTE_MATCHED -> DISCOVERY_REQUESTED
-> DISCOVERED_UNTRUSTED -> IDENTITY_VALIDATING -> POLICY_VALIDATED
-> GRANT_ISSUED -> FETCHING -> CONTENT_VALIDATING
-> INGESTION_PENDING -> INGESTED -> RETRIEVAL_REPLAYED
-> CITED_OR_SAFE_FALLBACK

DISCOVERED_UNTRUSTED | IDENTITY_VALIDATING | POLICY_VALIDATED |
GRANT_ISSUED | FETCHING | CONTENT_VALIDATING | INGESTION_PENDING
-> REJECTED (terminal)

CONTENT_VALIDATING | INGESTED -> QUARANTINED
```

`REJECTED` is terminal for that candidate/attempt. A newly and independently discovered identity gets
a new record; it does not revive a rejected candidate. TLS, identity, policy, parser, budget, source,
or grant failure is a safe failure, not an authorization bypass.

## 14. Validation and immutable ingestion

The validator compares policy-required normalized official fields: source, transport, external ID,
canonical path/origin, number, title, type, issuer, jurisdiction, dates, and required attributes. A
field may be optional only where the approved policy says so; missing data cannot silently downgrade
certainty.

Before ingestion, validate content type, decoded size, encoding, parser profile, identity agreement,
canonical URL/path, provenance, and content hash. Disable XML external entities and cap HTML/XML
nesting, nodes, attributes, text, decompression ratio, parser time, and bytes.

`IngestionService.ingest()` remains the sole ingestion route. It persists immutable document version,
chunks, source provenance, source/policy/grant correlation, fetch time, and hash. Same canonical
identity plus same hash is idempotent; same identity plus validated changed hash appends a new immutable
version. Historical cited versions are never overwritten.

## 15. Retrieval, citation, conversation, temporal

Every official answer keeps the canonical chain:

```text
immutable version/provenance -> source-isolated retrieval -> RetrievalRun
-> CitationRecord -> grounding evidence -> answer -> server citation revalidation
```

Revalidation proves persisted run/citation/chunk/version/provenance, active eligibility, requested
scope, and label. The LLM cannot invent metadata. Discovery data is never indexed or passed as
authoritative context before canonical ingestion.

Active policy and non-quarantine eligibility are required when selecting evidence for a new retrieval
run or creating a new answer. Resolution/revalidation of an already persisted historical run validates
its immutable run/citation/chunk/version/provenance identity regardless of later policy revocation or
quarantine. A UI may display a server-owned quarantine/status notice, but must not rewrite, erase, or
invalidate the historical citation chain.

Conversation remains bounded to recent turns, rolling summary, active topic, referenced document IDs,
and recent citation IDs. It never resends unlimited history. A duplicate-completed replay creates zero
provider, discovery, fetch, or ingestion calls. Conversation context cannot issue a grant.

Until M08.2 Phase B completes and is approved, `CURRENT_EFFECT` and `AS_OF` fail closed as
`UNSUPPORTED_TEMPORAL_SCOPE`. Acquisition cannot infer effect from title, date, priority, source text,
or LLM output. Afterwards, only reviewed complete relation/effect records select eligible immutable
versions; incomplete/conflicting data still fails closed.

## 16. Network, parser, and prompt security

- Enforce HTTPS and `verify=true`; no `verify=false`, HTTP downgrade, custom trust bypass, or
  diagnostic artifact in production paths.
- Resolve only registry-approved normalized DNS hosts; reject loopback, private, link-local, multicast,
  unspecified, and unexpected addresses under deployment policy.
- Disable redirects by default. Any future explicit redirect allowance requires same approved HTTPS
  origin/path, bounded hops, and reauthorization before follow.
- Never accept URLs, host/path, headers, SOAP actions, XML, credentials, identity, or grant values from
  user, channel, LLM, candidate, or fetched content.
- Apply connect/read/total timeouts, response/type/byte caps, compression limits, and parser isolation.
- Compile bounded safe normalization/match rules at policy load; reject unsafe regex and oversized fields.
- Treat question, user, retrieved, XML/HTML, title, metadata, and relationship text as untrusted data;
  none can modify policy, issue grants, invoke tools, or act as LLM instructions.
- Do not log secrets, raw channel IDs, raw questions, planner output, search terms, candidate text,
  fetched body, or provider payloads.

## 17. Persistence and migration proposal

This is a proposal **after M08.2 Phase B**, requiring separate user approval, schema review, migration
lifecycle proof, and privacy review. Add append-only records or equivalent tables:

| Record | Content | Must exclude |
|---|---|---|
| policy audit | policy/version/digest, registry digest, owner role, status, timestamps, reason code | secrets/raw user data |
| short-lived grants | grant ID, policy digest, identity digest, issue/expiry/use state | usable token/plain nonce |
| acquisition attempts | correlation ID, source/policy, state, counts, duration, outcome | raw question/planner/search/candidate/fetched text |
| quarantine | immutable version/candidate reference, reason, actor type, time | raw question/external payload |

Document provenance records source identity, policy revision/digest, grant correlation, fetch time, hash,
and validation outcome. Audit must never persist raw questions or hashes, planner JSON, search queries,
candidate text, provider payloads, raw Zalo payloads, raw IDs, or credentials.

Quarantine/revocation preserves historical versions, `RetrievalRun`s, and `CitationRecord`s for audit,
but excludes the affected version from future retrieval selection and new official answers. A remediation
requires an explicitly approved policy/version path.

## 18. Concurrency, idempotency, and controls

1. Coalesce equivalent gaps by policy digest and normalized candidate key.
2. Use advisory lock/lease on `(source_id, transport, action, canonical_external_id)` before grant use
   and before ingest; do not hold a DB transaction across external I/O.
3. Recheck policy, grant, canonical identity, and hash after lock.
4. Duplicate replay performs zero acquisition/ingestion/provider work.
5. Enforce budgets across coalesced work, not only each retry.
6. Apply source/policy rate limits and require a closed circuit before discovery/fetch.
7. Repeated TLS, validation, timeout, or upstream failures open a circuit and return source unavailable;
   never fail over to an unapproved source.
8. Equal identity/hash deduplicates; changed validated hash creates immutable new version.
9. Record only privacy-safe counts, duration, reason/state, version, budget, circuit, duplicate, and
   quarantine metrics.

Do not introduce queues, workers, crawler fleets, or a second distributed subsystem without measured,
separate approval.

## 19. Rollout and gates

### Phase 0 — Contract/compiler simulation

No network behavior. Validate schema/compiler, registry-subset proof, immutable digest, safe matchers,
rejection fixtures, and content-free audit model. Feature disabled.

**Oracle gate:** legal/source governance review. **User gate:** explicit contract/policy-envelope approval.

### Phase 1 — Exact-number controlled recovery

Enable only an actually supported TLS-valid source capability. Current VBQPPL can only be exact-number
recovery. Add grants, pre-I/O validation, budgets, canonical ingest, dedupe, and normal re-retrieval.

**Oracle gate:** TLS-valid adapter and security tests. **User gate:** explicit policy/cap activation.

### Phase 2 — Persistence, quarantine, and operations

After M08.2 Phase B, add approved migrations/audits/grants/acquisition/quarantine/locks/rate/circuit
controls where persistence is required.

**Oracle gate:** migration, privacy, concurrency, and revocation evidence. **User gate:** migration and
retention approval.

### Phase 3 — Additional deterministic official discovery

Only after a registry/adapter change proves a bounded official index/template. Enable one approved mode
at a time; no generic keyword, LLM, web-search, or crawler route.

**Oracle gate:** capability, SSRF/redirect/parser, and benchmark evidence. **User gate:** explicit
source/policy/template/budget approval.

### Phase 4 — Measurement and rollback

Measure against approved benchmarks. Temporal official-answer measurement awaits M08.2 Phase B. Rollback
disables policy activation/routes, preserves immutable history, and excludes revoked/quarantined content.

## 22. Good points, tradeoffs, residual risks, score

### Good points

- Replaces repeated document review with a reviewable bounded policy while retaining human authority.
- Retains ports, canonical ingestion, immutable provenance, source isolation, and citation integrity.
- Makes authorization explicit and rechecked at I/O, reducing SSRF/confused-deputy risk.
- Can improve repeat internal retrieval without treating discovery as evidence.

### Bad points / tradeoffs

- Compiler, grants, audit, revocation, locks, and routing add substantial authorization complexity.
- Strict policies provide less coverage than broad search and require governance maintenance.
- Synchronous acquisition increases latency and upstream dependence.
- Exact-number VBQPPL offers little for unknown title/concept questions; broad discovery now is YAGNI.

### Residual risks

- VBQPPL TLS remains blocked, preventing real automatic official expansion.
- Official content may be incomplete, malformed, delayed, or legally incomplete despite validation.
- Poorly governed narrow policies can still ingest irrelevant documents in their envelope.
- Legal-effect completeness remains dependent on M08.2 Phase B.
- Acquisition adds cost, source load, and operational review/revocation work.

| Category | M08.3.1 | M08.3.2 target | Reason |
|---|---:|---:|---|
| Boundary/security/citation fit | 9/10 | 9/10 | Retained ports and canonical chain |
| Data integrity | 8/10 | 9/10 | Deterministic validation, versioning, quarantine |
| Coverage potential | 6/10 | 8/10 | Policy-covered gaps may recover automatically |
| Simplicity/YAGNI | 8/10 | 5/10 | Authorization machinery is additional scope |
| Operational safety | 8/10 | 8/10 | Strong controls, more moving parts |
| **Overall** | **8.5/10** | **8.0/10** | Integrity improves; complexity/YAGNI cost lowers score |

Scores are target-design assessments, not implementation claims.

## 23. Acceptance criteria

- [ ] Versioned approved-source-policy contract validates fail-closed with owner/version/status/effective
  period/revocation and immutable compiled subset of registry/adapter authority.
- [ ] Broad rules, user URLs, freeform templates, unsafe matchers, and registry widening reject before I/O.
- [ ] Only server-issued short-lived grants can fetch; user/LLM/candidate inputs cannot make one.
- [ ] Grant/policy/registry/identity/TLS/endpoint/budget/rate/circuit revalidate before every I/O.
- [ ] Discovery remains non-evidence; official fetch is TLS-valid through `LegalSourcePort` only.
- [ ] Ingestion is immutable/versioned/provenanced and every official answer uses persisted normal
  `RetrievalRun → CitationRecord → citation revalidation`.
- [ ] Conversation replay remains bounded; completed replay does zero new acquisition work.
- [ ] User/internal evidence stays non-official and source-isolated.
- [ ] Temporal scopes fail closed until approved M08.2 Phase B support exists.
- [ ] Quarantine/revocation preserves historical citations but excludes future selection.
- [ ] Audit excludes raw questions, planner/search/candidate text, payloads, secrets, and raw channel IDs.
- [ ] Oracle and explicit user gates pass for every enabled rollout phase.

## 24. STOP conditions

Stop automatic discovery/fetch/ingestion and return a safe outcome if any of these applies:

```text
no effective compiled policy; invalid/broad/expired/suspended/revoked policy;
inactive/mismatched source, transport, host, endpoint, or action;
user/LLM/candidate URL, request, identity, or grant required;
no deterministic template/policy match; ambiguous/denied identity;
absent/forged/expired/consumed/revoked grant; failed pre-I/O check;
TLS, source identity, redirect, DNS/IP, timeout, parser, content, or provenance failure;
budget/rate/lease/coalescing/circuit failure; ingest or citation revalidation failure;
temporal request requiring incomplete M08.2 Phase B data;
user, institutional, guidance, test, or untrusted-discovery material presented as official law.
```

Never use `verify=false`, HTTP downgrade, unapproved fallback source, temporary official citation,
LLM-generated arbitrary search, or dynamic fetch authority as a workaround.

## 25. Final decision

**`GO_WITH_CONDITIONS`** for this architecture specification. Start only the smallest approved phase.
The immediate blocker is not policy syntax: it is the unavailable TLS-valid VBQPPL SOAP route and its
exact-number-only capability. Until an approved source/adapter route resolves that limitation, the
system may safely compile/reject policies but cannot claim automatic official title/concept discovery or
official corpus expansion.
